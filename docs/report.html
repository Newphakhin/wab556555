บทคัดย่อ (Abstract)

โปรเจกต์ Simple Booking System for Lab Room (ระบบจองห้องปฏิบัติการ สำหรับสาขาวิชาวิศวกรรมคอมพิวเตอร์ มหาวิทยาลัยกาฬสินธุ์) ได้รับการออกแบบและพัฒนาขึ้นเพื่อแก้ไขปัญหาการจองห้องปฏิบัติการซ้ำซ้อน การจดบันทึกด้วยเอกสารกระดาษหรือการแจ้งผ่านช่องทางแชทที่ไม่เป็นระบบ โดยพัฒนาเป็นเว็บแอปพลิเคชันแบบ Single Page Application (SPA) ด้วยเทคโนโลยี HTML5, CSS3 และ Modern JavaScript (ES Modules) ควบคู่กับการจัดเก็บข้อมูลในเบราว์เซอร์ด้วยฐานข้อมูล IndexedDB (LabBookingDB) สำหรับข้อมูลห้องและรายการจอง และ LocalStorage สำหรับจัดการเซสชันผู้ใช้และสิทธิ์ของผู้ดูแลระบบ

จุดเด่นของระบบคือการแยกโครงสร้างโค้ดออกเป็น 3 ชั้นอย่างชัดเจน ได้แก่ ชั้นส่วนติดต่อผู้ใช้ (Pages & Components), ชั้นบริการจัดการข้อมูล (Services) และชั้นกฎธุรกิจ (Domain Rules) โดยเฉพาะอัลกอริทึมตรวจสอบช่วงเวลาซ้ำซ้อน (new_start_time < existing_end_time AND new_end_time > existing_start_time) ที่ทำงานทั้งแบบ Real-time บนหน้าแบบฟอร์มจอง และตรวจสอบซ้ำในขั้นตอนการอนุมัติของผู้ดูแลระบบ ช่วยป้องกันปัญหาการอนุมัติห้องซ้ำซ้อนได้อย่างสมบูรณ์ นอกจากนี้ระบบยังผ่านการทดสอบด้วยชุดทดสอบอัตโนมัติ (Unit Tests) จำนวน 48 ชุดทดสอบ ครอบคลุมทุกเกณฑ์การตรวจรับ (Acceptance Criteria) ตามเอกสาร SRS ทุกประการ

บทที่ 1 บทนำและข้อกำหนดความต้องการของระบบ (SRS)

1.1 ชื่อโปรเจกต์และภาพรวมของระบบ (SRS ข้อ 1–2)

  • ชื่อโปรเจกต์ (ภาษาอังกฤษ): Simple Booking System for Lab Room
  • ชื่อโปรเจกต์ (ภาษาไทย): ระบบจองห้องปฏิบัติการสำหรับสาขาวิชาวิศวกรรมคอมพิวเตอร์ มหาวิทยาลัยกาฬสินธุ์

ภาพรวมของระบบ: Simple Booking System for Lab Room เป็นเว็บแอปพลิเคชันสำหรับจัดการการจองห้องปฏิบัติการของสาขาวิชาวิศวกรรมคอมพิวเตอร์ มหาวิทยาลัยกาฬสินธุ์ โดยมีวัตถุประสงค์เพื่อให้ผู้ใช้งาน เช่น นักศึกษา อาจารย์ หรือเจ้าหน้าที่ สามารถตรวจสอบห้องว่าง ส่งคำขอจองห้อง และติดตามสถานะการจองได้อย่างสะดวก ระบบนี้ช่วยลดปัญหาการจองซ้ำซ้อน การจดบันทึกด้วยเอกสารหรือช่องทางแชทที่ไม่เป็นระบบ และช่วยให้ผู้ดูแลสามารถตรวจสอบรายการจอง อนุมัติหรือปฏิเสธคำขอจองได้ง่ายขึ้น

1.2 วัตถุประสงค์ของระบบ (SRS ข้อ 3)

  1. เพื่อพัฒนาเว็บแอปพลิเคชันสำหรับจองห้องปฏิบัติการของสาขาวิชาวิศวกรรมคอมพิวเตอร์
  2. เพื่อให้ผู้ใช้สามารถตรวจสอบรายการจองและสถานะห้องได้อย่างสะดวก
  3. เพื่อป้องกันการจองห้องซ้ำซ้อนในวันและเวลาเดียวกัน
  4. เพื่อให้ผู้ดูแลระบบสามารถอนุมัติ ยกเลิก หรือปฏิเสธคำขอจองได้
  5. เพื่อฝึกให้นักศึกษาพัฒนาเว็บแอปพลิเคชันที่มี CRUD, validation, role-based view, calendar/table view และ dashboard อย่างง่าย
  6. เพื่อส่งเสริมให้นักศึกษาใช้ AI tools ช่วยวางโครงสร้างระบบ เขียนโค้ด แก้บั๊ก และจัดทำเอกสารประกอบโปรเจกต์

1.3 กลุ่มผู้ใช้งานและบทบาทผู้ใช้งาน (SRS ข้อ 4 และ ข้อ 7)

กลุ่มผู้ใช้งานหลักของระบบประกอบด้วย 4 กลุ่ม ได้แก่ (1) นักศึกษาสาขาวิชาวิศวกรรมคอมพิวเตอร์, (2) อาจารย์ประจำสาขาวิชาวิศวกรรมคอมพิวเตอร์, (3) เจ้าหน้าที่หรือผู้ดูแลห้องปฏิบัติการ และ (4) ผู้ดูแลระบบ โดยแบ่งสิทธิ์การใช้งานออกเป็น 2 บทบาทหลัก ดังนี้:

👤 7.1 บทบาทผู้ใช้งานทั่วไป (User)

  • ดูรายการห้องปฏิบัติการทั้งหมดที่เปิดให้จอง
  • ดูรายละเอียดห้อง (ความจุ อุปกรณ์ สถานที่ สถานะ)
  • ตรวจสอบตารางการจองรายวันและรายสัปดาห์
  • ส่งคำขอจองห้องพร้อมตรวจสอบเวลาซ้ำซ้อน
  • ดูสถานะคำขอจองของตนเอง (แยกตามอีเมลผู้จอง)
  • ยกเลิกคำขอจองของตนเอง หากยังไม่ถึงเวลาที่กำหนด

🛡️ 7.2 บทบาทผู้ดูแลระบบ (Admin)

  • เข้าสู่ระบบผู้ดูแลผ่านหน้า Login (#/login)
  • เพิ่ม แก้ไข และลบข้อมูลห้องปฏิบัติการ (CRUD)
  • ดูรายการคำขอจองทั้งหมดในระบบ
  • อนุมัติคำขอจอง (พร้อมตรวจซ้ำซ้อนอัตโนมัติ)
  • ปฏิเสธคำขอจองพร้อมระบุเหตุผลประกอบ
  • ยกเลิกรายการจอง และค้นหา/กรองรายการจอง
  • ดู Dashboard สรุปข้อมูลสถิติการใช้ห้องปฏิบัติการ

1.4 ขอบเขตของระบบ (SRS ข้อ 5–6)

1.4.1 ขอบเขตหลักที่ต้องทำ (Core Scope — ดำเนินการครบ 100%)

  1. แสดงรายการห้องปฏิบัติการที่สามารถจองได้
  2. แสดงรายละเอียดของห้อง เช่น ชื่อห้อง ความจุ อุปกรณ์ และสถานที่
  3. ผู้ใช้สามารถส่งคำขอจองห้องได้
  4. ผู้ใช้สามารถระบุวันที่ เวลาเริ่มต้น เวลาสิ้นสุด วัตถุประสงค์ และจำนวนผู้ใช้งานได้
  5. ระบบตรวจสอบการจองซ้ำซ้อนในห้องเดียวกัน วันเดียวกัน และช่วงเวลาเดียวกันได้
  6. ผู้ใช้สามารถดูรายการจองของตนเองได้
  7. ผู้ดูแลสามารถดูคำขอจองทั้งหมดได้
  8. ผู้ดูแลสามารถอนุมัติ ปฏิเสธ หรือยกเลิกคำขอจองได้
  9. ระบบสามารถแสดงตารางการจองรายวันหรือรายสัปดาห์ได้
  10. ระบบสามารถค้นหาและกรองรายการจองตามห้อง วันที่ หรือสถานะได้
  11. ระบบสามารถแสดง Dashboard สรุปจำนวนการจองตามสถานะได้
  12. Deploy ระบบให้สามารถใช้งานผ่าน URL ได้จริง

1.4.2 ขอบเขตเสริมที่ได้พัฒนาเพิ่มเติมในโปรเจกต์นี้ (Implemented Optional Features)

  • ระบบ Login แยกบทบาท User และ Admin: พัฒนาหน้า #/login พร้อมระบบป้องกันการเข้าถึงหน้า Admin (Route Guard adminOnly ตาม NFR-05)
  • ตารางการจองแบบ Visual Timeline (Day & Week Calendar View): คำนวณความสูงบล็อกตามเวลาจริงและจัดเรียงบล็อกที่เวลาซ้อนกันเป็นคอลัมน์ย่อย (Multi-lane layout)
  • โทนสี Dark Mode ระดับพรีเมียม: ออกแบบด้วย CSS Variables โทนสีเข้ม ลดความล้าของสายตาและอ่านง่ายในทุกขนาดหน้าจอ

1.4.3 สิ่งที่ไม่อยู่ในขอบเขต (Out of Scope สำหรับโปรเจกต์ 2 สัปดาห์)

ไม่เชื่อมต่อระบบทะเบียนนักศึกษาจริงหรือ LDAP/SSO ของมหาวิทยาลัย, ไม่ทำระบบอนุมัติหลายระดับ, ไม่คิดค่าบริการการใช้ห้อง, ไม่ทำ Native Mobile App, ไม่เชื่อมต่อ Google Calendar จริง และไม่ควบคุมอุปกรณ์ IoT หรือประตูห้องจริง

2.1 สถาปัตยกรรมของระบบ (Layered Client-Side Architecture)

1. Presentation Layer (UI)

  • index.html & css/style.css
  • js/app.js & js/router.js

  • js/services/bookingService.js

  • js/domain/rules.js (Pure Functions)

2.3 สถานะของการจองและกฎการจองเบื้องต้น (SRS ข้อ 12–13)

ระบบกำหนดสถานะของการจองออกเป็น 4 สถานะมาตรฐาน ได้แก่:

  • Pending (รออนุมัติ) — สถานะเริ่มต้นเมื่อผู้ใช้ส่งคำขอจองใหม่ รอการพิจารณาจากผู้ดูแลระบบ
  • Approved (อนุมัติแล้ว) — ผู้ดูแลอนุมัติให้ใช้งานห้องได้ และระบบจะล็อกช่วงเวลานี้ไม่ให้ผู้อื่นจองซ้ำ
  • Rejected (ไม่อนุมัติ) — ผู้ดูแลปฏิเสธคำขอจอง พร้อมบันทึกเหตุผลในฟิลด์ admin_comment
  • Cancelled (ยกเลิก) — รายการจองถูกยกเลิกโดยผู้จองเอง (ก่อนถึงเวลาเริ่ม) หรือยกเลิกโดยผู้ดูแลระบบ
กฎการจองเบื้องต้น 7 ข้อ (SRS ข้อ 13) ที่บังคับใช้ใน js/domain/rules.js:
  1. ผู้ใช้ต้องเลือกห้อง วันที่ เวลาเริ่มต้น และเวลาสิ้นสุดให้ครบถ้วน
  2. เวลาเริ่มต้นต้องน้อยกว่าเวลาสิ้นสุดเสมอ (toMin(start_time) < toMin(end_time)) และห้ามจองย้อนหลัง
  3. ไม่สามารถจองห้องที่อยู่ในสถานะ Maintenance (ปิดปรับปรุง) หรือ Closed (ปิดให้บริการ) ได้
  4. ไม่สามารถจองซ้ำกับรายการที่มีสถานะ Approved ในห้องเดียวกัน วันเดียวกัน และช่วงเวลาทับซ้อนกันได้
  5. คำขอจองใหม่ทุกใบมีสถานะเริ่มต้นเป็น Pending เสมอ
  6. ผู้ใช้สามารถยกเลิกคำขอจองของตนเองได้ เฉพาะเมื่อสถานะเป็น Pending หรือ Approved และยังไม่ถึงเวลาเริ่มใช้งาน
  7. Admin สามารถอนุมัติ ปฏิเสธ (ต้องระบุเหตุผล) หรือยกเลิกคำขอจองได้

2.4 เงื่อนไขการตรวจสอบเวลาซ้ำซ้อน (Time Overlap Logic — SRS ข้อ 14)

หัวใจสำคัญที่สุดของระบบจองห้องปฏิบัติการคือการป้องกันการจองเวลาทับซ้อนกันในห้องเดียวกันและวันเดียวกัน โดยระบบจะแปลงเวลาจากสตริง "HH:MM" เป็นจำนวนนาทีนับจากเที่ยงคืนด้วยฟังก์ชัน toMin(t) = h * 60 + m แล้วตรวจสอบด้วยอสมการคณิตศาสตร์ตามข้อกำหนด SRS ข้อ 14 ดังนี้:

new_start_time < existing_end_time   AND   new_end_time > existing_start_time

3.2 อธิบายโค้ดหลักส่วนที่ 1: กฎธุรกิจและการตรวจสอบเวลาซ้ำซ้อน (js/domain/rules.js)

ไฟล์ js/domain/rules.js เป็น Pure Functions ที่ไม่พึ่งพา DOM หรือฐานข้อมูล ทำให้สามารถนำไปทดสอบและอธิบายการทำงานได้อย่างชัดเจน: 

// 1. ฟังก์ชันแปลงเวลา "HH:MM" เป็นจำนวนนาทีนับจาก 00:00 (จาก js/utils/time.js)
export function toMin(t) {
  const [h, m] = String(t).split(':').map(Number);
  return h * 60 + (m || 0); // เช่น "09:30" -> 9*60 + 30 = 570 นาที
}

// 2. ฟังก์ชันตรวจสอบว่าช่วงเวลาใหม่ทับซ้อนกับช่วงเวลาเดิมหรือไม่ (SRS ข้อ 14)
export function isOverlap(newStart, newEnd, existingStart, existingEnd) {
  return toMin(newStart) < toMin(existingEnd) && toMin(newEnd) > toMin(existingStart);
}

// 3. ฟังก์ชันค้นหารายการจองที่ Approved แล้วซึ่งทับซ้อนกับคำขอใหม่ในห้องและวันเดียวกัน
export function findConflicts(bookings, { room_id, booking_date, start_time, end_time, excludeId = null }) {
  return bookings.filter(
    (b) =>
      b.status === 'Approved' &&
      b.id !== excludeId &&
      b.room_id === room_id &&
      b.booking_date === booking_date &&
      isOverlap(start_time, end_time, b.start_time, b.end_time)
  );
}

จุดสำคัญของการออกแบบ: พารามิเตอร์ excludeId ถูกออกแบบมาเพื่อรองรับขั้นตอนที่ Admin กดปุ่ม "อนุมัติ" รายการที่อยู่ในสถานะ Pending โดยระบบจะเรียก findConflicts ซ้ำอีกครั้งโดยไม่นับตัวมันเอง เพื่อป้องกันกรณีที่มีคำขอ Pending 2 รายการในเวลาเดียวกันแล้ว Admin เผลอกดอนุมัติทั้งคู่

3.3 อธิบายโค้ดหลักส่วนที่ 2: บริการจัดการการจอง (js/services/bookingService.js)

bookingService.js ทำหน้าที่เชื่อมโยงกฎจาก rules.js เข้ากับฐานข้อมูล IndexedDB โดยบังคับตรวจ Validation และตรวจเวลาซ้ำซ้อนทั้งตอนสร้างคำขอ (create) และตอนอนุมัติ (approve): 

export const bookingService = {
  /** สร้างคำขอจอง: 1) Validate ข้อมูล -> 2) ตรวจเวลาซ้ำซ้อน -> 3) บันทึกสถานะเริ่มต้นเป็น Pending */
  async create(input) {
    const room = await roomService.get(input.room_id);
    const errors = validateBooking(input, room);
    if (Object.keys(errors).length) return { ok: false, errors };

    const conflicts = findConflicts(await this.list(), input);
    if (conflicts.length) {
      return { ok: false, errors: { start_time: conflictMessage(conflicts) }, conflicts };
    }

    const now = new Date().toISOString();
    const booking = {
      id: uid('bk'),
      room_id: input.room_id,
      requester_name: input.requester_name.trim(),
      requester_email: input.requester_email.trim(),
      requester_type: input.requester_type,
      booking_date: input.booking_date,
      start_time: input.start_time,
      end_time: input.end_time,
      purpose: input.purpose.trim(),
      number_of_users: Number(input.number_of_users),
      status: 'Pending',
      admin_comment: '',
      created_at: now,
      updated_at: now,
    };
    await db.put('bookings', booking);
    return { ok: true, booking };
  },

  /** Admin อนุมัติ — ตรวจทับซ้อนซ้ำอีกครั้งก่อนเปลี่ยนสถานะเป็น Approved */
  async approve(id) {
    const b = await this.get(id);
    if (!b) return { ok: false, error: 'ไม่พบรายการจอง' };
    if (b.status !== 'Pending') return { ok: false, error: 'อนุมัติได้เฉพาะรายการที่รออนุมัติ' };
    const conflicts = findConflicts(await this.list(), { ...b, excludeId: b.id });
    if (conflicts.length) return { ok: false, error: conflictMessage(conflicts) };
    const updated = await this._update(id, { status: 'Approved', admin_comment: '' });
    return { ok: true, booking: updated };
  },
};

5.1 สรุปผลการพัฒนาโปรเจกต์และผลลัพธ์การเรียนรู้ (SRS ข้อ 18 และ ข้อ 24)

จากการพัฒนาโปรเจกต์ Simple Booking System for Lab Room ระบบสามารถทำงานได้ครบถ้วนตามเกณฑ์ Minimum Viable Product (MVP) ทั้ง 11 ข้อ และบรรลุผลลัพธ์การเรียนรู้ (Learning Outcomes) ทั้ง 10 ข้อตามเอกสาร SRS ได้แก่:

  • พัฒนาเว็บแอปพลิเคชันที่มีฟังก์ชัน CRUD ทั้งข้อมูลห้องปฏิบัติการและข้อมูลการจองได้อย่างสมบูรณ์

  • พัฒนา Role-based View แยกมุมมองผู้ใช้งานทั่วไป (User) และผู้ดูแลระบบ (Admin) พร้อมระบบป้องกันสิทธิ์เข้าถึง
  • สร้าง Dashboard สรุปข้อมูลสถิติและตารางแสดงผลเวลาการจองรายวัน/รายสัปดาห์ที่รองรับหน้าจอมือถือ (Responsive UI)
